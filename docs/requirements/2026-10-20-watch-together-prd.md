# Техническое задание: совместный видеоплеер для macOS и Windows

Product Requirements Document

Technical Specification

v1.0 — 20.10.2026

Концепция: десктопное приложение, объединяющее функциональность VLC с возможностью синхронного просмотра локального видео несколькими пользователями через интернет.

Главное отличие от существующих решений — пользователям не требуется загружать видео в облако, иметь одинаковые файлы на компьютерах или запускать собственный сервер вручную.

Один участник выбирает файл, создаёт комнату и отправляет приглашение. Остальные подключаются и смотрят то же видео с синхронным управлением.

## 1. Основные принципы продукта

Полноценный локальный плеер

Поддержка MP4, MOV, MKV, нескольких аудиодорожек, субтитров, перемотки, скорости и полноэкранного воспроизведения.

Совместный просмотр без дополнительных действий

Создание комнаты в один клик. Достаточно отправить другу ссылку или код приглашения.

Видео хранится на устройстве владельца

Приложение передаёт необходимые части файла участникам без обязательной предварительной загрузки на внешний сервер.

Общее состояние воспроизведения

Пауза, запуск, перемотка и изменение скорости согласуются между всеми участниками комнаты.

## 2. Ключевой технический момент

Здесь важно разделить два процесса, которые часто путают:

1. Передача видео. Друзьям нужно получать видеоданные с устройства владельца файла.
2. Синхронизация плееров. Приложение должно согласовывать таймкод, паузы, перемотку и другие команды.

Передавать только команды недостаточно: без видеоданных остальные участники ничего не увидят.

Предлагаемая архитектура

Упрощённая логическая схема. В реальной сети соединение может быть прямым или проходить через ретранслятор.

Предлагаю гибридную модель: сервер комнаты действительно работает на компьютере создателя, но для удобного подключения через интернет допускается небольшой внешний сервис установления соединений и резервная ретрансляция трафика.

Это сохраняет принцип локального хранения, но решает проблему NAT, роутеров и сетевых ограничений. Прямое P2P-соединение не гарантируется для всех пользователей, а TURN/relay позволяет соединяться там, где прямой канал недоступен.&#x20;

### 3.3. Комнаты совместного просмотра

Создание комнаты

1. Пользователь открывает видео.
2. Нажимает «Смотреть вместе».
3. Приложение создаёт локальный сервер комнаты.
4. Генерируется уникальная ссылка и код подключения.
5. Владелец отправляет приглашение друзьям.

Подключение участника

1. Пользователь открывает приложение.
2. Вставляет ссылку или код приглашения.
3. Приложение подключается к комнате и начинает буферизацию.
4. После готовности воспроизводится то же видео с актуального таймкода.

Для MVP комната рассчитана на 2–5 участников, включая хоста. Это проектное ограничение, а не предел технологии.

### 3.4. Права управления

Предлагаются два режима:

- Свободное управление: любой участник может поставить паузу, продолжить воспроизведение или перемотать фильм. Изменения видят все.
- Управление хостом: управлять общим просмотром может только создатель комнаты.

Переключение режима доступно хосту.

Индивидуальные настройки — громкость, полноэкранный режим, выбор аудиодорожки и субтитров — не синхронизируются. Они не должны мешать другим участникам.

Скорость воспроизведения, напротив, синхронизируется глобально, чтобы фильм не расходился по времени.

## 4. Синхронизация воспроизведения

Это одна из основных технических задач проекта. Простая отправка команды `play` всем клиентам не обеспечивает синхронность: участники получают сообщения с различной задержкой и могут иметь разные скорости декодирования.

### 4.1. Принцип работы

Сервер хоста хранит авторитетное состояние комнаты — единственную версию текущего таймкода и статуса воспроизведения.

Пример состояния:

```

{
  "roomId": "R7K2M9",
  "revision": 142,
  "mediaId": "sha256-or-session-id",
  "playback": {
    "status": "playing",
    "positionMs": 125000,
    "speed": 1.0,
    "updatedAtServerMs": 1792537200000
  },
  "permissions": {
    "control": "everyone"
  }
}

```

Участники получают обновления через WebSocket. Клиент учитывает серверное время, оценку задержки соединения и собственное состояние буферизации.

### 4.2. Алгоритм синхронизации

Целевые пороги рассинхронизации

MVP

0–100 мс

Без коррекции

100–500 мс

Плавная коррекция скорости

Более 500 мс

Точная перемотка к целевой позиции

Предлагаемые начальные настройки алгоритма, которые необходимо уточнить в ходе сетевых испытаний.

Ключевые требования:

- Heartbeat и сверка позиций каждые 1–2 секунды.
- Измерение задержки и оценка сдвига часов через обмен временными метками.
- Команды получают порядковый номер `revision`, чтобы устаревшее сообщение не отменило новое.
- Команды исполняются относительно серверного времени.
- Новые участники подключаются к текущему состоянию комнаты, а не к началу фильма.
- После восстановления соединения клиент повторно синхронизируется с сервером.

При буферизации одного участника по умолчанию остальные продолжают просмотр. У зависшего клиента отображается состояние «Буферизация», после восстановления он возвращается к общему таймкоду.

Для MVP целевая рассинхронизация в стабильных сетевых условиях — не более 250 мс между участниками. Это критерий приёмки, а не гарантия на любом соединении.

## 5. Передача видео через интернет

### 5.1. Предлагаемая реализация

Вместо захвата экрана и перекодирования видео в прямом эфире используем передачу исходного медиафайла частями.

Преимущества:

- Сохраняются исходные аудио- и видеодорожки.
- Субтитры остаются доступными для индивидуального выбора.
- Не требуется постоянно кодировать видео на компьютере хоста.
- При перемотке можно запрашивать нужные участки файла.
- Декодирование происходит локально у каждого участника.

Для этой схемы подходит HTTP byte-range streaming: клиенты запрашивают определённые диапазоны байтов, а сервер хоста читает их из файла и отправляет по защищённому соединению. Движок плеера должен поддерживать такой способ чтения.

### 5.2. Сетевое подключение

| Компонент                  | Назначение                                                   |
| -------------------------- | ------------------------------------------------------------ |
| Локальный сервер           | Доступ к выбранному файлу и управление комнатой              |
| Signaling service          | Помогает участникам найти друг друга и установить соединение |
| Direct connection          | Передача данных напрямую, когда сеть позволяет               |
| Relay fallback             | Резервная передача данных через внешний узел                 |
| WebSocket                  | Синхронизация команд и участников                            |
| TLS / защищённый транспорт | Защита соединения и передаваемых данных                      |

Нужно учитывать, что для прямой передачи видео через HTTP и для WebRTC DataChannel используются разные транспортные модели. Точный способ их объединения фиксируется после сетевого прототипа.

### 5.3. Ограничения

Скорость интернета создателя комнаты напрямую влияет на качество просмотра.

Например, для фильма с битрейтом 8 Мбит/с при четырёх удалённых участниках хосту может потребоваться примерно 32 Мбит/с исходящей полосы плюс сетевые накладные расходы, если каждому отправляется отдельный поток.

Поэтому необходимо реализовать:

- Буферизацию вперёд на клиенте.
- Ограничение количества участников на комнату.
- Индикатор качества соединения.
- Обработку временного падения скорости.
- Запрос новых диапазонов файла при перемотке.
- Отдельное отображение ошибок декодирования и ошибок сети.

Автоматическое снижение качества через транскодирование не включается в первую версию. Оно существенно увеличивает сложность и нагрузку на компьютер хоста.

| Слой                | Технология         | Назначение                             |

### 8.1. Основные программные модули

Media Engine — загрузка и декодирование видео, получение метаданных, список дорожек, управление воспроизведением.

Room Server — создание и уничтожение комнат, учёт участников, полномочия, хранение состояния и обработка команд.

Media Stream — доступ к выбранному файлу, поддержка byte-range запросов, чтение данных без копирования всего файла в память.

Sync Engine — расчёт текущего таймкода, разрешение конфликтующих команд, компенсация задержек и коррекция рассинхронизации.

Network — установление соединений, переподключение, шифрование и переключение между прямым каналом и ретрансляцией.

### 8.2. События протокола

| Событие              | Направление   | Назначение                    |
| -------------------- | ------------- | ----------------------------- |
| `room.create`        | Client → Host | Создать комнату               |
| `room.join`          | Client → Host | Подключиться                  |
| `room.state`         | Host → Client | Получить актуальное состояние |
| `playback.play`      | Client → Host | Запросить воспроизведение     |
| `playback.pause`     | Client → Host | Запросить паузу               |
| `playback.seek`      | Client → Host | Запросить перемотку           |
| `playback.speed`     | Client → Host | Изменить общую скорость       |
| `playback.updated`   | Host → All    | Применить новое состояние     |

| `sync.ping`          | Client ↔ Host | Измерить задержку             |

Сервер проверяет каждую входящую команду и только затем изменяет состояние комнаты. Участники не применяют запрос другого пользователя как окончательную команду без подтверждения хоста.

## 9. Безопасность и жизненный цикл комнаты

Приложение получает доступ только к конкретному видеофайлу, который выбрал владелец. Оно не должно открывать остальную файловую систему компьютера.

Обязательные требования:

- Уникальный непредсказуемый токен комнаты, отдельно от короткого отображаемого кода.
- Авторизация каждого запроса на получение видеоданных.
- Защищённое соединение с участниками.
- Ограничение количества подключений и частоты команд.
- Возможность исключить участника и отозвать приглашение.
- Удаление временных токенов после закрытия комнаты.
- Отсутствие автоматического сохранения постоянной копии видео на клиенте.
- Завершение серверного процесса после закрытия комнаты.

При выключении компьютера хоста или закрытии его приложения просмотр прекращается для всех. Передача роли хоста другому участнику не поддерживается в MVP, поскольку исходный файл находится у первоначального владельца.

## 13. Что сознательно остаётся за пределами MVP

Не включаем пользовательские аккаунты, друзей и контакты, облачное хранение фильмов, стриминг экрана, голосовые комнаты, чат, мобильные приложения и перекодирование на лету.

Также не требуется история просмотренных файлов, сложная медиатека, плейлисты и интеграция с торрент-клиентами.

После выпуска базовой версии эти возможности добавляются независимо от основного ядра.

## 15. Итоговое техническое решение

Для первой версии я предлагаю разделить разработку на два независимо проверяемых результата: полноценный локальный плеер и сетевое ядро совместного просмотра.

Основная архитектура — локальный сервер у хоста, передача исходного видео по диапазонам байтов, синхронизация по WebSocket, прямое подключение при возможности и relay fallback.

Самый важный технический эксперимент — не дизайн и даже не воспроизведение видео, а возможность стабильно открыть большой локальный MKV на другом компьютере через интернет, перематывать его и сохранять доступ ко всем дорожкам без транскодирования. Пока этот сценарий не работает, полноценную разработку интерфейса и комнат лучше не масштабировать.

Для первого релиза результат считается готовым, когда два пользователя на разных операционных системах и в разных сетях могут открыть один фильм, синхронно управлять просмотром и независимо выбирать аудио и субтитры.
