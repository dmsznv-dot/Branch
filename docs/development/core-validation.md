## Уточнения, принятые при реализации

1. **Дедупликация до конца действительности команды.** Запись хранится до `issued_at+120000 ms`, а не фиксированные 120000 ms после получения. Разрешённый timestamp из будущего увеличивает время хранения максимум до 122000 ms. Иначе возникает окно повторного выполнения. Цена: до 2 секунд дополнительного хранения/ограничения при неизменном лимите 256 записей на сессию.
2. **Повторное использование getrandom 0.4.** Вместо планового 0.3 используется уже закреплённый OS-CSPRNG 0.4.3. Это убирает дублирование библиотеки без уменьшения размера/случайности токена. Риск решения: возможная platform/API несовместимость потребует отката; целевые ОС ещё не запускались.
3. **Лимит watch-подписок на входе.** Сохранён заданный API сырого `tokio::watch::Receiver`: максимум восемь при допуске, существующие clones учитываются при новом subscribe. Доверенный Rust-код технически может клонировать Receiver самостоятельно. Если handles станут доступны недоверенному коду, потребуется wrapper без Clone для абсолютного лимита объектов.
4. **Атомарная lifetime-запись через arc-swap 1.9.3.** CAS заменяет целый live timestamp либо terminal None; устаревшее решение об expiry не отменяет успешное продление. Сохраняется полный u64 и отсутствуют unsafe reclamation/room mutex в чтении. Цена: зависимость и Arc allocation/CAS на продление; производительность на целевых устройствах не измерялась.
5. **Локальное право завершения комнаты.** Узкая непередаваемая по wire `CreatedRoom.owner` позволяет LocalRoomSession закрыться после TTL host session. Сетевой close сохраняет сессионную авторизацию. Цена: дополнительный API и lifetime-владение; отдельный regression проверяет закрытие, отзыв гостя и освобождение ресурсов после expiry.

Политика observed expiry сохранена: активное чтение проверяет срок перед I/O и выдачей данных; явный kick/close/media replacement немедленно уведомляет ожидающих. Само продвижение ManualClock без последующего обращения не является таймером пробуждения dormant waiter.

## Конфигурация и границы доказательств

Инструкции среды используют существующий checkout, workspace-local toolchain и оригинальный `scripts/setup-core.sh` с TLS/checksum verification. Публикация не выполнялась: пользователь должен проверить и сохранить изменения в настройках среды, затем опубликовать её. Сохранение draft не применяет runtime изменения и не доказывает восстановление нового cloud task.

Выполнено только на Linux x86_64. CI workflow для Linux/Windows/macOS добавлен, но hosted jobs здесь не запускались. На других ОС sparse allocation требует отдельной проверки; fixture там явно ignored. Нативные libmpv/Tauri, GPU/fullscreen/DPI, установщики, WebRTC direct/TURN, реальные разные сети и измеренная синхронность ≤250 ms относятся к B/C/D. Проценты покрытия и vulnerability scan не измерялись и не заявляются.

Во время отмены уже начатый kernel file operation может закончиться внутри Tokio; новые байты после проверки отзыва не выдаются. Уже переданные байты отозвать нельзя. Shutdown возвращает явный timeout при превышении двухсекундного deadline, затем всё равно ожидает abort/join cleanup; это не hard real-time гарантия.
